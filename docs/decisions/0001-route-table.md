# 0001: Data routes and a closed handler dispatcher

Date: 2026-10-22. Issue: BND-3. Status: accepted for M2/M3.

Use a reusable data table that maps route patterns to application-owned tags. Pass a closed top-level dispatcher as a template and give every handler a runtime environment containing startup channels. M2 returns a tag and captured params; M3 invokes the handler, middleware and validation associated with that tag.

This keeps the router independent of function ownership and leaves its table available to the spec router, trie, proofs and manifest exporter. It costs a second declaration connecting tags to handlers. The prototype is an experiment, not the M2 router or a public API implementation.

## The three shapes

All three compiled programs are generated by [`generate.py`](../../prototypes/0001-route-table/generate.py). Their common operations are in [`shapes.bend`](../../prototypes/0001-route-table/shapes.bend); the benchmark and network shell are in [`runtime.bend`](../../prototypes/0001-route-table/runtime.bend). These representative excerpts use the actual prototype names. Run the generated files for complete imports and startup code.

### Template list

```python
import Base
import ../shapes.bend as S

def h1(nonce: U32) -> U32:
  (1 + nonce : U32)

def h2(nonce: U32) -> U32:
  (2 + nonce : U32)

def routes() -> List<S.FnRoute>:
  [S.FnRoute{"/r001", h1}, S.FnRoute{"/r002", h2}]

def dispatch(path: String, nonce: U32) -> U32:
  S.template_list(~routes(), path, nonce)
```

This reads closest to the plan's registration sketch. `FnRoute` is `Type`, because it contains a function, and its list is affine. The closed template constructs a fresh list for each dispatch, which the traversal consumes; this construction and disposal are included in the measurement. It cannot become the reusable runtime routing table just by adding `+`.

Bend 2.0.38 rejects a direct 500-element `~[...]` argument with `expected: a ~ argument that stops growing`. A named closed `~routes()` compiles at 500; the generator uses that form at every size. This is a limit of the tested spelling, not evidence that template lists cannot support 500 routes.

### Data table and tag dispatcher, selected

```python
import Base
import ../shapes.bend as S
import ../runtime.bend as R

def routes() -> List<&2, S.Route>:
  [S.Route{"/r001", 1}, S.Route{"/r002", 2}]

def serve_h1(env: R.Env) -> IO(String):
  R.respond(env, 1)

def serve_h2(env: R.Env) -> IO(String):
  R.respond(env, 2)

def invoke(tag: U32, env: R.Env) -> IO(String):
  match tag:
    case 1:
      serve_h1(env)
    case 2:
      serve_h2(env)
    case _:
      IO.pure(String, "missing")

def app(env: R.Env, path: String) -> IO(String):
  R.Env{counter, table, counting} = env
  +t = table
  invoke(S.data_walk(t, path), R.Env{counter, t, counting})
```

`main` calls `R.run(~app, ~bench_dispatch, routes(), 50)`. The table is constructed once, then shared through `Env`. `app` is closed: the startup channel is an ordinary argument, never a captured local in a `~` expression. Every matched branch calls a distinct top-level IO handler with that environment. The pure benchmark also includes a tag switch calling a route-specific pure handler, not just the table search.

This shape needs explicit tags and a dispatcher, so it repeats some registration information. Use an application-owned `Data` sum type with named constructors in the real API, rather than the spike's numeric tags and catch-all. Keep the dispatcher beside the table until code generation can emit both from one declaration. Do not promise a function-valued mutable route registry.

### Template chain

```python
import Base
import ../shapes.bend as S

def h1(nonce: U32) -> U32:
  (1 + nonce : U32)

def h2(nonce: U32) -> U32:
  (2 + nonce : U32)

def last(path: String, nonce: U32) -> U32:
  S.chain(~h2, ~S.missing, "/r002", path, nonce)

def dispatch(path: String, nonce: U32) -> U32:
  S.chain(~h1, ~last, "/r001", path, nonce)
```

The handler and continuation are closed top-level definitions. Request values travel as runtime arguments. The generated definitions run from the last route upward, respecting Bend's definition order. This avoids an affine route list, but hand-written chains are awkward to inspect and registration order is encoded in code. Changing to a trie would require generating different code, and a separate data description is still needed for manifests and schemas.

In the initial set of three repeats, the largest individual deviation from its metric's median was 21.2%. At 500 routes, data dispatch takes about 52% of the list's mixed cost, while the chain is about 11% faster than data. HTTP throughput at 500 is about 20,250 req/s for data against 16,811 for the list and 21,753 for the chain.

The chain wins the dispatch and binary-size comparison. Choose data despite that advantage: its measured overhead is acceptable for the reference router, and its copyable metadata gives M2/M3 one representation for routing, proofs, schemas and manifests. Revisit the lookup algorithm in M2 rather than encoding registration order permanently in a template chain.

These are costs of the tested linear exact-path implementations, not a prediction of trie performance. HTTP includes parsing, serialization, IO scheduling and a same-VM load generator. It should corroborate the in-process measurements, not determine the route representation alone.

### Method

The Boat sandbox was `default`: 4 vCPU, 8 GB RAM, AMD Ryzen 9 9950X under KVM, x86-64 Ubuntu. Bend is pinned to 2.0.38; oha is 1.8.0. Exact CPU, memory and compiler details, build durations, binary bytes, checksums and all oha JSON responses are retained in [`results.json`](../../prototypes/0001-route-table/results.json).

All variants register the same fixed-width ASCII paths `/r001` through `/rNNN` in increasing order and use `String.eq`. Mixed dispatch visits every route equally, in descending order per cycle. Last-hit dispatch repeats `/rNNN`; the miss is `/r999`. There are no params, schemas or middleware in these timings. Each handler returns its distinct route number; a miss returns zero in the pure test. The data case includes its tag dispatcher. The network bodies contain the route number, with the data case's unmatched route returning `missing`.

Path lists are constructed and forced before timing. A bounded native batch repeatedly traverses them and accumulates an observable checksum. The mixed checksum must equal `iterations * (routes + 1) / 2`, the last-hit checksum `iterations * routes`, and the miss checksum zero, modulo 2^32. The harness checks these independently. `IO.now` is monotonic with millisecond resolution. Each sample uses a pilot to target about 750 ms for mixed dispatch, bounded between 20,000 and 2,000,000 requests and rounded to complete route cycles. The timed cost includes workload-list traversal and one checksum print, with no baseline subtraction. It excludes startup and path creation.

The programs run with `+RTS --threads 1`. No compute parallelism is used, so extra compute threads would not accelerate the single IO event loop. After a response check and one second of HTTP warm-up, oha runs for three seconds with 50 keep-alive connections against the last route. The actor exists at startup but receives no messages during throughput measurements. Every measured HTTP sample must have success rate 1. The three shapes rotate order across three repeats; the table reports medians. There is no claim about long-running tail latency or performance on a different CPU.

The build column reports the median of two full `bend generated/SHAPE-500.bend -o bin/SHAPE-500` invocations, one in each complete benchmark run, including checking, C generation and native compilation with Bend's default flags. Bytes are the unstripped executable size. Each executable contains both benchmark and server entry modes. The data variant includes a separate IO tag dispatcher; the other variants reuse their pure route-specific handler before the common IO response helper.

A second complete invocation after rerunning the pinned setup script reproduced all 36 per-request medians (three pure workloads and HTTP throughput for nine cases) within 20%; the largest deviation was 17.7%. The two 500-route builds of each shape produced identical binary sizes. The second build's time differs from the displayed two-build median by at most 9.6%. Individual timings are noisier than the medians, so compare the full three-repeat runs.

The second raw run is [`reproduced.json`](../../prototypes/0001-route-table/reproduced.json). Check it against the original with:

```sh

# PASS: all 36 median metrics within 20%; maximum deviation=17.67%
```

## Environment and shared state

The actual prototype environment is `Env{counter: Chan(Message), table: List<&2, Route>, counting: Bool}`. Startup creates the counter channel, spawns one actor owning a `U32` count, builds the route table, and calls the accept loop with that environment and the closed `~app`. Each spawned connection receives a copy of `Env`; channel copies refer to the same actor.

Each counter-mode handler sends `Add{reply}` through `env.counter`, then waits on its own fresh reply channel. The actor increments serially and acknowledges the new value. A `Read{reply}` control message returns the current count without changing it. Sends and receives are checked, and per-request reply channels are closed after use.

`verify.py` first starts a normal server and requests all 50 routes, checking each distinct body and a miss. It then starts a fresh counter-mode process, explicitly opens 50 sockets, synchronizes 50 workers, and sends 20 sequential requests on each unchanged socket. It checks that replies are exactly the set 1..1000 and that a read through `/__count` returns `1000`. Warm-up and normal route checks use a different process, so they cannot inflate the count. There are no retries.

Observed output:

```text
PASS data-50: all 50 route-specific responses, plus miss
PASS counter: 50 unchanged sockets x 20 = 1000; replies 1..1000; final read=1000
```

`correctness.bend` separately gives duplicate `/same` registrations different results: all three choose 11 from the first registration, rather than 22 from the second. All three return zero on an absent path. Run it with `bend prototypes/0001-route-table/correctness.bend -o /tmp/bnd3-correctness && /tmp/bnd3-correctness`.

## Handoff to M2 and M3

M2 owns reusable route data: registration index, method set, compiled pattern, handler tag and data metadata. Matching returns either a typed routing error or a match containing the selected tag and decoded params. Keep first-match registration order as the semantic rule. A trie may change the search structure but must return the same match as the spec router; neither router needs handler functions. HEAD fallback and 405 remain M2 work.

M3 owns a closed dispatcher with the conceptual signature `dispatch(tag, env, ctx) -> IO(Res)`. The app calls pure matching, puts params on `ctx`, and invokes that dispatcher through its template boundary. Store channels, startup configuration and mounted-app state travel in `env`; params and request-local variables travel in `ctx`. Handlers receive both. Multiple apps may have different environment and tag types; library entrypoints must abstract over those `Data` types and the closed dispatcher. The prototype fixes them only to keep the experiment small.

Attach global, group and per-route middleware identifiers as ordered data lists in the route metadata. M3 resolves those identifiers to top-level middleware definitions through a closed dispatcher. Compose the selected route's onion chain for one request: an affine `next` closure is allowed if it is consumed at most once. Do not store that closure in the reusable table or try to pass it as a closed template. Enforce the single-use continuation in the middleware type; early returns omit it. The counter spike verifies environment delivery, not middleware composition or post-handler hooks.

Attach params, query, headers, body and response schema descriptions to the same route metadata. Those descriptions must be copyable data so matching and manifest generation can inspect them. Where decoding produces different Bend types, the handler-tag branch selects a top-level typed decoder and then the matching typed handler; do not erase heterogeneous typed handlers into function fields on `Route`. Middleware identifiers and schema descriptions can be inherited and flattened when groups are assembled. Keep registration indexes stable so metadata stays attached to the same handler after trie compilation. M4 owns the actual schema representation and decoder contract.

The list spelling can remain a future convenience declaration if tooling emits the data table and closed dispatcher from it. It is not the runtime storage contract. No macro or generator feature for user apps is implemented here.

## Limits and verification boundary

This spike matches only exact static paths. It does not implement real routing, params, methods, mounting, middleware, schema validation, manifests, timeouts or HTTP security. The common shell buffers split headers and supports sequential small ASCII GET requests with `Content-Length` responses. It does not support pipelining, request bodies, general framing or header limits. It binds only inside its host/VM and must not be deployed as an HTTP server.

No existing laws were changed. The pure dispatch helpers terminate by structural recursion; actor and accept/connection loops use `@unsafe` only for ongoing IO. The root quality gate remains `timeout --foreground 10m bun run check`; observed output includes `Bend version OK: bend 2.0.38`, `ALL PROOFS CHECK`, successful TypeScript checking, and `1 pass / 0 fail` for the scaffold HTTP integration test. The prototype's real server and actor are verified separately by the commands above.

Both complete runs used sandbox `bx_hsbu8hy7`. It was deleted with `boat-sbx gc --label bnd-3-route-table`; the follow-up labeled listing was empty.
